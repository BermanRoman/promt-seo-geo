# Инфраструктура

## Как вести
- **Одно действие за раз**: что нажать, где, что вписать. Ждать «готово» или скриншот. Проверить самим (`node engine/scripts/doctor.mjs`, `ssh`, `curl`, API) и только потом следующий шаг.
- Человек застрял — попросить скриншот и показать, куда нажать.
- **Ключи и пароли** — только в `workspace/.env` (права 600) и `workspace/.secrets/`. В чат, коммиты и логи их не выводить; если человек прислал ключ в чат — записать в `.env` и попросить потом перевыпустить его. Пароли от панелей система не берёт и не вводит.
- Шаги с пометкой «по желанию» можно пропустить: сайт работает и без них.
- Хостинг может временно не пускать по SSH после частых подключений: не долбить повторами, проверки собирать в одну команду; если не пускает — дать человеку готовую команду для его терминала.

## 1. Домен и хостинг
**Путь А (сайта нет).** Предложить 3–5 свободных имён в зоне .ru (коротко, имя или тема автора, без дефисов; проверить `whois <домен>`). Хостинг — любой виртуальный хостинг с доступом по SSH: сайт статический, хватит самого простого тарифа.
Рекомендация — сказать прямо и один раз: «Мы сами работаем на Рег.ру. Это партнёрская ссылка: если зарегистрируетесь по ней, автор системы получит небольшой процент, вам это ничего не стоит, а промокод даёт скидку 5% на первый заказ домена или хостинга. Можно взять и любой другой хостинг с SSH». Ссылки: домен — https://www.reg.ru/domain/new/?rlink=reflink-32609077, хостинг — https://www.reg.ru/hosting/?rlink=reflink-32609077, промокод `4D0A-BA5D-5270-8274`. Ничего не открывать за человека, не вставлять ссылку больше одного раза, не уговаривать.
**Путь Б (сайт есть).** Поддомен (например `blog.домен.ru`): в панели хостинга создать сайт на поддомене или у регистратора добавить A-запись поддомена на IP хостинга. Старый сайт не трогать.
**Сертификат.** В панели хостинга включить бесплатный Let's Encrypt для домена (или поддомена). Проверка: `curl -sI https://<домен>` — ответ без ошибки сертификата.
**Веб-сервер.** Узнать, кто отдаёт сайт: Apache (часто за nginx) или чистый nginx — в панели хостинга в настройках сайта или по заголовку `Server` в `curl -sI`. Правила в `.htaccess` (заголовки безопасности, кэш, 301, своя 404) работают только с Apache; на чистом nginx они молча игнорируются. Если сайт на чистом nginx, а `.htaccess` нужен — попросить человека переключить обработчик сайта на Apache в панели (обычно это пункт «обработчик» или «PHP» в настройках сайта). После любых правил — проверить их `curl -sI` по главной и по странице: есть ли `Content-Security-Policy`, `Cache-Control`, работает ли 301.

## 2. SSH-доступ для заливки
1. Создать ключ: `ssh-keygen -t ed25519 -f ~/.ssh/<короткое-имя>_deploy -N "" -C "<домен> deploy"`.
2. Показать человеку **публичный** ключ (`.pub` — его можно показывать) и объяснить, куда вставить: в панели хостинга раздел «SSH-ключи» или «Доступ по SSH»; включить SSH, если он выключен.
3. Записать алиас в `~/.ssh/config` (`Host <имя>`, `HostName`, `User`, `IdentityFile`, `IdentitiesOnly yes`) — хост и логин человек берёт в панели.
4. Проверка: `ssh -o BatchMode=yes <имя> 'pwd; ls'` — найти папку сайта (часто `www/<домен>`).
5. В `workspace/.env`: `DEPLOY_HOST=<имя>`, `DEPLOY_DIR=<папка>`.
6. Пробная выкладка с закрытой индексацией: `cd engine && npm run deploy`, затем `curl -s -o /dev/null -w "%{http_code}" https://<домен>/` — должно быть 200.

## 3. Яндекс Метрика
1. Человек создаёт счётчик на metrika.yandex.ru: адрес сайта, включить «Вебвизор», «Контентная аналитика» (тип разметки — Schema.org, JSON-LD). Код счётчика вставлять не нужно — только прислать номер.
2. Номер — в `site.config.json` → `metrikaId`.
3. Цели (тип «JavaScript-событие»): `cta_material`, `cta_explainer`, `cta_home`, `cta_author` — нажатие главной кнопки; `explainer_to_material` — переход из разбора в материал; `read_to_end` — долистал до конца; `read` — дочитал (3+ минуты). Если подключён MCP yandex-ads (`yd_metrika_goal_create`) — создать их самим, иначе дать человеку список.

## 4. Яндекс Вебмастер
1. webmaster.yandex.ru → «Добавить сайт» → адрес с https. Способ подтверждения — **мета-тег**: прислать код из `content="…"` → `site.config.json` → `yandexVerification` → `npm run deploy` → в Вебмастере «Проверить».
2. «Индексирование → Файлы Sitemap»: `https://<домен>/sitemap-index.xml`.
3. «Настройки → Привязка к Метрике» — привязать счётчик и включить «Обход по счётчикам».
4. По желанию — API (переобход новых страниц и статистика в сводках): oauth.yandex.ru → создать приложение с правами `webmaster:hostinfo` и `webmaster:verify`, получить токен → `.env` → `YANDEX_WEBMASTER_TOKEN`. Проверка: `cd engine && node scripts/webmaster.mjs setup`. API Вебмастера иногда лежит по несколько дней — тогда пропускаем, страницы подождут в очереди.

## 5. Google Search Console
1. search.google.com/search-console → «Добавить ресурс» → «Ресурс с префиксом в URL» (`https://<домен>/`) → способ «Тег HTML»: код → `googleVerification` → выкладка → «Подтвердить». (Есть доступ к DNS домена — можно доменный ресурс, тогда `gscProperty: "sc-domain:<домен>"`.)
2. «Файлы Sitemap» → `sitemap-index.xml`.
3. По желанию — API для сводок: Google Cloud → проект → включить Search Console API → сервисный аккаунт → ключ JSON → положить в `workspace/.secrets/gsc.json` (права 600) → в Search Console «Пользователи и разрешения» добавить e-mail аккаунта с правами «Полный». Проверка: `node scripts/gsc.mjs status`.

## 6. Bing Webmaster
1. bing.com/webmasters → импорт сайта из Search Console (самый быстрый способ).
2. По желанию — API: «Settings → API Access» → ключ → `.env` → `BING_WEBMASTER_KEY`. Проверка: `node scripts/bing.mjs status`. Индекс Bing питает ChatGPT и Copilot — это важно для цитирования нейросетями.

## 7. IndexNow и веб-архив
- IndexNow (Яндекс и Bing узнают о новых страницах сразу): `node scripts/doctor.mjs indexnow` — ключ создаётся сам. У каждого сайта и поддомена свой ключ: ключ, общий с другим сайтом человека, IndexNow отвергает ответом 403. Если человек перенёс `.env` с другого сайта — убрать оттуда `INDEXNOW_KEY` и создать новый.
- По желанию — archive.org (снимок каждой страницы с датой — подтверждение авторства): archive.org/account/s3.php → `IA_ACCESS_KEY`, `IA_SECRET_KEY` в `.env`.

## 8. Роботы нейросетей
`robots.txt` движка открывает сайт всем роботам, но хостинг может закрыть часть из них раньше, на уровне веб-сервера: по умолчанию некоторые хостинги сбрасывают соединение у GPTBot, ClaudeBot, Amazonbot и SEO-краулеров. Тогда нейросети не видят сайт, хотя в `robots.txt` всё открыто.
1. Проверка с компьютера, одной командой: `for ua in GPTBot OAI-SearchBot ChatGPT-User ClaudeBot Claude-SearchBot PerplexityBot Amazonbot Applebot YandexBot Googlebot bingbot; do printf '%s ' $ua; curl -s -o /dev/null -w '%{http_code}\n' -A "Mozilla/5.0 (compatible; $ua)" https://<домен>/robots.txt; done`. Нужно 200 у всех; `000` (сброс) или 403 — блок хостинга. Роботы живых ответов (важнее всего): OAI-SearchBot, ChatGPT-User, Claude-SearchBot, PerplexityBot, YandexBot, Googlebot, bingbot; обучение моделей: GPTBot, ClaudeBot. `Google-Extended` и `YandexAdditional` в список не входят: это правила robots.txt, своих заходов у них нет.
2. Журнал доступа на сервере (если сайт уже работает) — тем же единственным заходом по SSH, что и остальные проверки: строки с именами роботов и кодами 499, 403 или 0 байт ответа.
3. Блок есть — дать человеку готовое обращение в поддержку хостинга: какой робот, какой адрес, что отвечает сервер (строка из журнала или вывод проверки), просьба разблокировать для этого сайта. Отправляет человек. После ответа — проверить снова.
Сканеры уязвимостей, инструменты нагрузки и SEO-краулеры (AhrefsBot, SemrushBot, MJ12bot и т. п.) сайту не нужны — их блок оставить. Для сайтов в России робот Meta (`meta-externalagent`) не просить открывать: Meta признана в РФ экстремистской.

## Финал
`node engine/scripts/doctor.mjs` — всё обязательное с ✓. Коммит в `workspace/` (без `.env` и `.secrets` — проверить `.gitignore` внутри workspace: `.env`, `.secrets/`). Дальше — этап `design`.
