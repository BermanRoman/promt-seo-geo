# Безопасность системы и сайта

**Зачем этот файл и кто его читает.** Здесь правила обращения с ключами и доступами, деплоя, заголовков сайта и действий при утечке или взломе. Читают мастер установки (заводит ключи и доступы), агент-разработчик сайта (заголовки, скрипты, деплой), скрипты деплоя и проверки, оркестратор (перед каждым коммитом и публикацией) и любой агент, который работает с API поисковиков, Метрики и хостинга. Эти правила не отменяются ни решением автора, ни удобством.

**Главное.** Статический сайт без PHP, базы данных и админки снимает почти все взломы через сайт. Реальные риски: угон аккаунта хостинга или регистратора, утечка ключа (API, SSH), подмена DNS, DDoS, жалобы на контент, копирование текстов.

## 1. Ключи и секреты

| Правило | Как |
|---|---|
| Где лежат | Только в `workspace/.env` и `workspace/.secrets/`. Обе папки в `.gitignore` репозитория системы, вся `workspace/` тоже. В репозитории — только `.env.example` с пустыми значениями |
| Чего не делать | Не печатать ключ в чат, в лог, в отчёт, в сообщение коммита, в комментарий кода, в URL. Не вставлять ключ в код и в конфиг сайта, который попадает в сборку |
| Как передавать | Скрипт читает ключ из окружения сам. Агент вызывает скрипт, но значение не выводит. Если нужно показать, что ключ есть, — только «задан / не задан» или последние 4 символа |
| Ввод ключа | Ключ вводит человек: сам вписывает его в `workspace/.env` или в запрос, который пишет в этот файл. Агент не просит прислать ключ в чат |
| Перед коммитом | Проверка на секреты (`gitleaks` или аналог) как pre-commit хук. Нашёл — коммит не делается |
| Права | Минимальные: токен только с нужными правами (чтение, где хватает чтения). У MCP рекламных и аналитических кабинетов есть инструменты, которые удаляют счётчики, сегменты и кампании; если сервер поддерживает режим «только чтение» (например, `YD_READONLY=true` у yandex-ads), включить его — решение владельца кабинета |
| Сборка | В `dist/` не попадают `.env`, `.git`, `*.map`, служебные файлы. Сервер отдаёт 404 на `.env`, `.bak`, `.sh`, `.log`, `.sql`, `.ini` и скрытые файлы (кроме `.well-known`) |

## 2. SSH и деплой

- **Отдельный ключ `ed25519` на каждый хостинг**, с парольной фразой. На macOS фраза хранится в Связке ключей (`ssh-add --apple-use-keychain`, в `~/.ssh/config`: `UseKeychain yes`).
- В `~/.ssh/config` для хоста: `IdentitiesOnly yes`, `StrictHostKeyChecking yes`. Отпечаток ключа хоста сверить с панелью хостинга при первом входе.
- В `authorized_keys` на сервере — префикс `restrict`, если хостинг его поддерживает [проверить: rsync и sftp обычно работают без pty].
- Открытый FTP не использовать. Только SSH/SFTP/rsync по ключу.
- Скрипт деплоя выгружает только `dist/` с исключениями. Перед выгрузкой — проверка на секреты.
- **Частые подключения.** Некоторые хостинги блокируют SSH на часы после серии подключений. Заливку, проверки и чтение логов собирать в один сеанс, а не открывать соединение на каждую операцию.
- Ключ не синхронизируется в облака; диск компьютера зашифрован (FileVault, BitLocker).

## 3. Аккаунты, домен, DNS

Делает человек один раз, система напоминает и проверяет:
- Уникальные пароли из менеджера паролей для хостинга, регистратора, почты, поисковых консолей.
- Двухфакторная аутентификация везде, где есть. Если 2FA только по SMS — спросить у оператора про запрет замены SIM без личного визита.
- Заполненные контакты владельца аккаунта у хостинга: без них доступ не восстановить.
- Отдельная почта для хостинга и регистратора со своей 2FA.
- Домен: автопродление, продление заранее; подтверждённая личность администратора (у регистраторов `.ru` — через Госуслуги; по данным регистраторов, без этого с 01.09.2026 блокируются продление и смена NS [проверить у регистратора]). В WHOIS нет домашнего адреса и телефона.
- Письма «о смене администратора» или «подтвердите перенос», пришедшие не из личного кабинета, игнорировать.
- DNS-зону (A, MX, TXT, NS) сверять с эталоном раз в неделю или месяц — это делает скрипт.

## 4. Сайт: что работает в браузере посетителя

- **Никакого сбора персональных данных**: нет форм, комментариев, регистрации, подписки по email, чатов. Контакт с автором — через его публичный канал.
- **Единственный внешний скрипт по умолчанию — Яндекс Метрика.** Других счётчиков, пикселей, виджетов соцсетей, внешних шрифтов и CDN нет. Добавить внешний скрипт — только по прямому решению автора, с правкой CSP.
- Движок встраивает код счётчика и стили прямо в страницу (так быстрее). Если включаете CSP, разрешите встроенные скрипты и стили (`'unsafe-inline'` для `script-src` и `style-src`) или пропишите их хеши — иначе CSP сломает Метрику.
- Кнопок «поделиться» с иконками Facebook и Instagram нет (`legal-ru.md`).

**Заголовки безопасности**
- HTTPS принудительно (настройка панели хостинга или редирект), www → без www одним прыжком.
- `Strict-Transport-Security` с `max-age=31536000`; без условия `env=HTTPS`, если перед Apache стоит nginx (за прокси Apache видит HTTP, и заголовок с таким условием не появится). `preload` не ставить: его трудно отменить.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` с запретом камеры, микрофона, геолокации, платежей, USB.
- **CSP** разрешает только свой домен и домены Метрики (`mc.yandex.ru`, `yastatic.net`, `mc.yandex.*`, `mc.webvisor.*` и `wss://` для них, `frame-src blob:` для Метрики). JSON-LD CSP не блокирует.
- **`X-Frame-Options` не ставить**: Вебвизор показывает сайт в iframe из `metrika.yandex.*`, и заголовок его сломает. Вместо него — `frame-ancestors` со списком доменов Метрики.
- Порядок выката CSP: неделю `Content-Security-Policy-Report-Only`, смотреть консоль, визиты в Метрике и записи Вебвизора, потом боевой заголовок.
- Если перед Apache стоит nginx, заголовки из `.htaccess` к статике (css, js, картинки) могут не применяться. Проверять `curl -I` по HTML и по статике.

## 5. Мониторинг и целостность

- Внешний мониторинг доступности (бесплатный тариф любого сервиса) раз в 5 минут, уведомления в два канала: мессенджер и почта.
- Проверка с российского IP: ответ 200, заголовки, срок SSL.
- **Контроль целостности** при «Проверь сайт»: сравнение `engine/dist/` с сервером (`rsync -nci --delete`). Расхождение, которого не было в заливке, — тревога (возможный дефейс).
- Раз в неделю: DNS и NS против эталона, срок SSL и домена.
- В Метрике включено «Фильтровать роботов».
- Поисковых и ИИ-ботов не блокировать. Конкретный бот грузит сервер — блок по User-Agent или IP; лимиты запросов заранее не включать: они могут задеть поисковики.

## 6. DDoS и бэкапы

- Базовая защита хостинга обычно бесплатна (фильтрация L3/L4). Защиту от HTTP-флуда (L7) и выделенный IP докупать при первой атаке или перед громкой публикацией. Если сайт касается политики, хостинги прямо советуют постоянную фильтрацию.
- Источник правды — `workspace/` под git (навык «Знакомство» создаёт там локальный репозиторий; удалённый — только приватный): сайт пересобирается из него за минуты. Бэкапы хостинга нужны для того, что вне git (`.htaccess`, настройки панели) и для разбора инцидента.
- Снять страницу за минуту (жалоба, требование регулятора): `draft: true` в её файле или удалить файл, затем заливка — `rsync --delete` уберёт страницу с сервера.

## 7. Если ключ утёк

Утёк — значит попал в чат, лог, коммит, публичный репозиторий, скриншот или чужие руки. Даже если «никто не видел».
1. **Сразу отозвать ключ у провайдера** и выпустить новый. Это первый шаг, а не последний: удаление из истории git не отменяет того, что ключ уже скопирован.
2. Новый ключ записать в `workspace/.env` (или `.secrets/`); проверить, что старого нет нигде в рабочих файлах.
3. Посмотреть журнал использования у провайдера за период с момента утечки: чужие вызовы, изменения, расходы.
4. Если ключ попал в коммит — убрать из истории (`git filter-repo` или аналог) и перезаписать удалённую ветку, предупредив владельца репозитория. Ключ при этом всё равно считается скомпрометированным.
5. SSH-ключ: удалить старый публичный ключ из `authorized_keys` на сервере, выпустить новый, проверить `authorized_keys` на чужие ключи.
6. Записать инцидент в журнал `workspace/`: что утекло, когда, что сделано. Сообщить владельцу одной строкой.

## 8. Если сайт взломан или подменён

1. С **другого** устройства сменить пароль хостинга, проверить 2FA, контакты, историю входов.
2. Сменить пароль панели хостинга. Удалить чужие ключи из `authorized_keys`. Если есть подозрение на компьютер автора — выпустить новый SSH-ключ, старый удалить.
3. Проверить в панели cron-задания, FTP-пользователей, `.htaccess`, лишние файлы. Сохранить копию заражённой папки для разбора.
4. Залить чистую сборку из git с удалением лишнего (`rsync --delete`).
5. Сверить DNS-зону, NS, сертификаты.
6. В Яндекс Вебмастере открыть «Безопасность и нарушения», при необходимости запросить перепроверку; отправить главные страницы на переобход. То же в Search Console.
7. Написать в поддержку хостинга.

## 9. Копирование и негативное SEO

- Защиту от копирования на JS не ставить. Доказательство авторства — быстрая индексация (IndexNow сразу после публикации), `datePublished` в разметке и снимок archive.org.
- С копировщиками: жалоба их хостеру и жалоба в поисковик на нарушение авторских прав.
- Спам-ссылки на сайт обычно просто не учитываются; disavow в Google — только при ручной санкции.
- Накрутка поведенческих факторов конкурентами: сохранять скриншоты всплесков в Метрике, писать в поддержку Вебмастера с доказательствами, встречной накруткой не отвечать.
- Контактную почту, на которую хостинг пересылает жалобы, читать ежедневно: сроки по требованиям регулятора — сутки и меньше.
